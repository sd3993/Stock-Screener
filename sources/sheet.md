# The Google Sheet: access and layout

## Google Sheets (`gws` CLI)
Scripts reach the sheet with Google's `gws` CLI (googleworkspace/cli, v0.22.5, not an officially supported Google product), no model tokens.
- **Install and login:** `C:\Users\sd391\AppData\Local\Programs\gws\gws.exe` (on the user PATH). OAuth client "gws-cli" (Desktop app) in the user's Google Cloud project, published "In production" so the login doesn't lapse after 7 days; its `client_secret.json` and the encrypted login live in `C:\Users\sd391\.config\gws\` (never open or copy them). Logged in as the sheet's owner with the Sheets scope only (`gws auth login -s sheets`, which prints a link the user opens on this computer). `gws auth status` shows the account, scopes and storage. Other projects reuse the same client; more scopes means a new login with more `-s` services. The login renews itself past the access token's 1-hour life, without a browser.
- **Calls:** output is JSON; exit codes 0 ok, 1 API error, 2 auth error, 3 validation. Read: `gws sheets spreadsheets values get --params '{"spreadsheetId": "<id>", "range": "Data!A1:E3"}'`. Writes use the same Discovery form (`values update`/`append`/`batchUpdate` with `--params` and `--json`); send values with `"valueInputOption": "RAW"` so tickers, codes and dates aren't converted the way typed input is (strings such as "TRUE", "00123", "2026-11-03 21:30" and "=1+1" stay text, numbers stay numbers, JSON `true` becomes a boolean, which checkbox-style columns and `=$Q2=TRUE` rules need); `values batchUpdate` takes `--params '{"spreadsheetId": …}'` and `--json '{"valueInputOption": "RAW", "data": [{"range": …, "values": …}]}'`; use numeric sheetIds for formatting, and read back to verify.
- Old verdicts (before 23 Oct 2026) are in the Drive copy "Stock Screener (archive, old verdicts as of 23 Oct 2026)".

## The sheet (`1yBV2fZiIR9xgZ3r-5feDKF_urqXspkPLLG9wPDoPtDU`)
Final outcomes only; the user reads it only when told all changes are in place. Light colours only, related columns merged to limit horizontal scrolling.
- **Tabs and sheetIds:** Short term 101, Medium term 102, Long term 103, Allocation 7, Holdings 104, Pending results 105 (renamed each quarter; its name is in Data!BA1), Data 106, Data Flags 10. Formulas are pre-filled (Data rows 2-300, horizon tabs 2-200, Holdings/Allocation 2-100). Which columns each step writes: `/workflow/s14_listing.md` (Data, Data Flags, Pending) and `/workflow/s15_allocation.md` (Holdings, Allocation), through `sheet_write.py` and `kite_holdings.py` (scripts write the sheet directly through `gws`); every other column is a formula and is never written.
- **Formula columns (never written):** Data AD:AZ, BA, BD; Holdings A, E, G:L, R, S, W:Y; Allocation A, F, G, J:M, R, S, W:Y
  (`sheet_write.py` reads this line and refuses a column map that touches one; keep it on one line, tabs separated by ";". Data BA holds only the pending tab's name in BA1; Allocation P1:S4 is the horizon-share block, with text in P and Q.)
- **Data:** one row per analysed company; written columns A:AC, BB, BC, BE (Horizon), BF (Stage) (`/workflow/s14_listing.md`). Formula columns AD:AZ and BD: live price chain, P/E now, forward P/E, PEG, multiples and CAGR per horizon (base multiple = horizon-end base EPS × exit P/E + dividends, ÷ live price; CAGR over 2/5/7 years), bear multiples, short-term target price and % to target, re-rating share, pending flag, data-flag flag, held flag. BA1 holds the pending tab's name.
- **Horizon tabs** (Short term, Medium term, Long term): live formula views of Data (hidden column Z is the sorted ticker list), sorted by expected CAGR, descending. A company is listed on a tab when its Data flag for that horizon (K, O or S) is Y and its non-negotiables aren't Fail; S14 sets only the flag of the company's one horizon (the visibility rule of `/principles/investing_rules.md`); a holding whose horizon test doesn't hold is listed on the tab named in Data BB. Price moves never remove a row: when the live price breaks a rule (CAGR < 25%, bear < 0.8x, forward P/E ≥ 50 or negative, PEG > 2 or negative), or the company fails a non-negotiable or its horizon test doesn't hold (holdings), the row's text turns red and "Below rule (live)" lists every reason. Short term also has target price, % to target and a sell-trigger cell; medium and long show exit P/E and re-rating share. Rows may still link to the company's other horizon tabs (left from the nested layout).
- **Allocation:** S15's actions with live price, current value and horizon links; F1:S4 shows each horizon's share of target and current value against its range (built to count a position flagged in several horizons equally in each; with one flag per company each position counts wholly in its horizon). The range text in Q2:Q4 copies the allocation and rebalancing rule of `/principles/investing_rules.md`; update it whenever that rule changes.
- **Holdings:** S15's status per holding with live price, value, P&L and horizon links.
- **Listing filters:** those in Short term!Z2 and Medium term!Z2 still list a stock on a longer horizon's flag; changing them waits for the user's decision.
- **Live price chain:** GOOGLEFINANCE (`NSE:SYM` or `BOM:<code>`); if N/A, screener.in's price via IMPORTXML from the "Screener URL" column (a sheet formula, not a research source); if that fails too, the stored price from the last S14.
- **Colours, one meaning each** (a cell colour overrides the row colour on that cell; red text combines with any fill): row light yellow = results pending; ticker cell light red = data flag (links to the company's first row in Data Flags); price cell light orange = screener price, light grey = stored price; sell-trigger cell light green = short-term target hit; Holdings Qty and Avg-cost cells light blue = Kite didn't refresh; red text = a rule broken (reasons in "Below rule (live)").
