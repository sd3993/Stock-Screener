# Zerodha Kite (Kite CLI)
Official CLI from zerodha/kite-cli (MIT; never the unofficial `kitecli` PyPI package or jogendra/kite-cli).
- **Read-only:** use the Kite CLI strictly read-only (holdings, positions, orders and trades lists, profile, margins, quotes). Never place, modify, cancel or delete any order of any type (regular, AMO, GTT, alerts, MF, conversions) or write anything else to the account, unless the user explicitly asks for that specific action in chat.
- **Not a blocker:** if Kite is unavailable (e.g. not logged in during an unattended run), carry on with the last fetched holdings (`data/kite/holdings.csv`, or the sheet's Holdings tab) and come back to it later (holdings only change the amount left to reach each target, not the targets).
- **Holdings:** fetched from Zerodha Kite only: in full at the start of each run (S1), so holdings go through the normal process, and re-checked for new trades in S15. If the gate or S13 makes a holding a full exit, or S11 finds an integrity flag on one, tell the user straight away, without waiting for S15.
- **Install:** v0.2.1, from the GitHub release zip `kite-<version>-x86_64-pc-windows-msvc.zip` (check its SHA-256 against the release's `checksums.txt`); `kite.exe` is in `C:\Users\sd391\AppData\Local\Programs\kite\` (on the user PATH only; open a new terminal). Update the same way.
- **Login (the user types it in their own terminal; the agent never runs it, asks for or types the user ID, password or 2FA):** `kite auth login` (optionally `kite auth login AB1234`). It prompts in the terminal for user ID, password (masked), a 2FA method and the TOTP/OTP code; needs an interactive TTY and refuses `--json` or piped input. Then `kite doctor` checks the session (one read-only call, `GET /user/margins`). Logout: `kite auth logout` (only if the user asks).
- **Session:** stored in `%APPDATA%\kite\config.json` (`kite config path` prints it) as `user_id` and `access_token`; no password or 2FA is stored. Never read or print that file, `KITE_ACCESS_TOKEN` or `KITE_API_KEY`. The token expires daily around 06:00 IST (sooner if another login or logout invalidates it) and is not renewed, so the user logs in again each day; after expiry `kite doctor` can still show the session set while the API answers TokenException 403, and `kite_holdings.py` exits 3. After login, commands run non-interactively and share the session.
- **Read-only commands (always with `--json`):** `kite --json user profile`, `kite --json user margins [--segment equity]`, `kite --json portfolio holdings`, `kite --json portfolio positions` (`net` and `day` arrays), `kite --json orders list`, `kite --json orders trades`, `kite --json mf holdings`, `kite --json market ltp NSE:INFY`, `kite --json market resolve NSE:INFY`, `kite --json doctor`. On success the JSON is the bare result (holdings: a list of objects); errors come as `{"ok": false, "error": {...}}` on stdout; exit 0 ok, 1 runtime/API error, 2 usage error. Holdings JSON: `tradingsymbol`, `quantity`, `t1_quantity`, `collateral_quantity`, `mtf.quantity`, `last_price` (combine the quantities for the full position).
- **Holdings script:** `python scripts/kite_holdings.py` (S1 and before S15) writes the same holdings to two copies: `data/kite/holdings.csv` (latest: sym, exchange, isin, name, qty, avg_cost, last_price, google_code, screener_url, fetched_at) plus `data/kite/holdings_<date_time>.json` (the CLI's answer), outside the runs and git-ignored; and the sheet's Holdings tab through gws (RAW), data columns only: Z Ticker, B Name, C Qty, D Avg cost, N Google code, O Screener URL, P Stored price, Q Kite stale (FALSE), V ISIN (header "[h] ISIN"), and the fetch time (IST) in the Notes header cell, M1: "Notes · Kite fetched YYYY-MM-DD HH:MM" (column M is 260 px wide so it isn't clipped; if Kite is unavailable M1 keeps the last real fetch; `--latest` parses the time from M1, falling back to the old U1 if M1 has none). It never writes F Status or the Notes cells M2 down (S15's) and never deletes rows. Rows match by ISIN (column V), else by ticker; a new holding takes the first row with Z empty; a sheet holding no longer in Kite gets Qty 0 (S15 removes the row). It reads the tab back and checks Qty, Avg cost and the stamp.
  - Values: qty = `quantity` plus any T+1, collateral and MTF quantities (not yet seen in a real answer, so it prints CHECK when one appears, to confirm against Kite web once). Stored price = Kite's `last_price` at the fetch. Name, Google code and screener URL: from the Data tab's row for the ticker when S14 has written one; otherwise name from `scr/overview.json` or Kite's instrument name (`market resolve`, title-cased abbreviation, e.g. "Action Const Equip"), code `NSE:<sym>` / `https://www.screener.in/company/<sym>/consolidated/` when the symbol resolves on NSE, else `BOM:<code>` / `.../company/<code>/consolidated/`, the BSE code being the holding's BSE `instrument_token` >> 8 (checked: ACE 532762, Kilburn 522101, Kama 532468).
  - What it does when Kite or gws is unavailable, `--latest` and the test overrides: its `--help`.
- **Price history:** `kite --json historical candles --instrument-token <token from market resolve> --interval day --from "YYYY-MM-DD 00:00:00" --to "YYYY-MM-DD 00:00:00"` returns daily OHLCV back to at least 2006 on the normal login (no paid Kite Connect plan), split/bonus-adjusted (RELIANCE 2 Jan 2006 close 82.4). Only instruments Kite lists today (no delisted companies). Read-only; a second price source for checking artefacts.
- **Never run:** `orders place|modify|cancel`, `portfolio convert`, `gtt place|modify|delete`, `alerts create|modify|enable|disable|delete`, `request post|put|delete`, `kite auth login|logout`, `kite` or `kite tui` (interactive), `stream ticks` without a limit. Writes are dry runs unless `--confirm`; in this project they are not run at all (the user decides trades).
- **Errors and rate limits:** on `MissingSession`/`session expired` ask the user to run `kite auth login`. On `CloudflareBlocked` wait and retry later, no loops. Rate limits: quotes 1/s, historical 3/s, other REST 10/s; no automatic retry.
