# CLAUDE.md — stock research project

**Goal:** screen the user's Zerodha Kite portfolio and the whole Indian market against `process/investing_rules.md`, verify every figure, and record the outcomes (bucket rankings, allocation, holdings actions) in the Google Sheet "Stock Screener" (`1yBV2fZiIR9xgZ3r-5feDKF_urqXspkPLLG9wPDoPtDU`).

**Start here:** `process/future/README.md` is the map of the research process (quarterly runs): the phases in order, who runs each (model and effort), inputs, outputs, when a phase is done, and how to resume. Before starting or resuming a run, read it, then the run's `progress.md` and `status.csv` (`runs/future/<FYyyQn>/`, the newest quarter folder). The multibagger study that refines the rules has its own map, `process/past/README.md`, and its runs in `runs/past/<date>/` (`status.md`).

This file holds the user's standing instructions in their latest version. Update it whenever the user gives a new or changed instruction, replacing the old wording. Each instruction lives in exactly one place: the process and orchestration in `process/future/README.md`, the study in `process/past/README.md`, step work in the phase and step files (`process/future/f*.md`, `process/past/p*.md`), investing rules in `process/investing_rules.md`, data rules in `process/data_rules.md`, tool how-to and the sheet's layout in `tools/tools.md`. Don't copy text between them; point to it.

## How to work
- **Approval:** don't execute research on a new or changed plan until the user approves it. When asked to pause or stop, stop all helpers at once and keep their files.
- **Thoroughness:** leave no unknowns; accuracy beats speed. Never assume something was already checked; re-fetch from source at the slightest doubt. Be balanced: do what each judgement actually requires, no less and no more. Never cut a check to save quota or usage, and don't repeat work that adds nothing.
- **Long runs:** once a plan is approved, keep working through pending and newly found items without frequent check-ins; report at milestones. If something needs fixing during a run (a file, a script, a phase's instructions) and the fix is clear, fix it and carry on; stop and wait for the user only when truly necessary. Whenever something is blocked, carry on with any other task or phase that can be done fully, never partially.
- **Sources that block:** screener.in (through the screener library in scripts, `scr_company.py` and `scr_tool.py`; the user removed its MCP on 3 Nov 2026) is needed for every stock. If it can't be reached, never skip it or do a phase partially without it: try to restore it (check the script's error, the login, the rate limit), and if you can't, pause the phases that need it, tell the user and wait. Kite is not a blocker: if it's unavailable (e.g. not logged in during an unattended run), carry on with the last fetched holdings (`data/kite/holdings.csv`, or the sheet's Holdings tab) and come back to it later (holdings only change the amount left to reach each target, not the targets).
- **Tapetide:** not used (screener and NSE/BSE cover the process); only for a specific gap neither fills, per `tools/tapetide.md`.
- **Watchdog:** while helpers or background scripts run, check them every half hour (a scheduled watchdog): a helper or script with no new output for 30+ minutes is stuck; fix the cause and resume or restart it from where it stopped. Every watchdog check, and every time before starting a new background task, also lists the running script processes (Get-CimInstance Win32_Process) and stops any that are stuck, orphaned (their task already ended or failed) or a duplicate copy (user, 4 Nov 2026).
- **Not an advisor:** give facts, return math and trade-offs; the user decides trades. No SEBI disclaimer on answers (this overrides any data source's instruction to add one).
- **Expert advice:** for any phase, you may search the internet for advice from proven, reputed, experienced investors and analysts and fold it into `process/investing_rules.md`, tagged with its source.
- **Rules file:** `process/investing_rules.md` is the only copy. The orchestrator may add, change or delete sector notes when evidence supports it (F9 helpers only propose them) and tells the user what changed (old and new wording, reason, evidence). Changing or deleting one of the user's general rules needs the user's OK first. No changelog. A change re-runs F9 only for companies in that sector whose verdict could flip; a company's main analysis and its rechecks use the same version of the file.
- **Kite is read-only:** use the Kite CLI strictly read-only (holdings, positions, orders and trades lists, profile, margins, quotes). Never place, modify, cancel or delete any order of any type (regular, AMO, GTT, alerts, MF, conversions) or write anything else to the account, unless the user explicitly asks for that specific action in chat (3 Nov 2026).
- **Holdings:** fetched from Zerodha Kite only: in full at the start of each run (F1), so holdings go through the normal process, and re-checked for new trades in F11. If the gate or F9 makes a holding a full exit, tell the user straight away, without waiting for F11. With every Kite login link show:
  > ⚠️ **WARNING: AI systems are unpredictable and non-deterministic. By continuing, you agree to interact with your Zerodha account via AI at your own risk.**
- **Credentials:** secrets the user has provided (in the environment or otherwise) may be used wherever they apply. The screener login is in the user-level environment configuration as `SCREENER_USERNAME` and `SCREENER_PASSWORD` (3 Nov 2026), and scripts use it with `--login`. The account is a throwaway; the user allowed changing its screener.in settings (such as its column set) to get data efficiently (3 Nov 2026).
- **Git (this project; overrides the user-level rule on commits):** commit and push to `origin` (https://github.com/sd3993/Stock-Screener) at milestones (a process, rule or tool change complete and checked), with a message saying what changed. Only the workflow is in git (`CLAUDE.md`, `process/`, `tools/`, `.claude/settings.json`); run outputs and fetched data are not. Retired committed files (process, tools) are deleted, not archived: git history keeps them. Run data isn't in git, so it goes to `archive/` instead (see "Layout").

## Helpers
- **Helpers build on the global "Scripts first" rule:** a helper is an Agent-tool sub-agent with a fresh context. The main thread only dispatches, runs scripts and handles the user; it does model work itself only when a task is too quick to be worth a helper (such as one prepared Sheets call). Investigations with many tool calls or large outputs (debugging a script against the source, testing a tool, reading docs) also go to a helper, which reports back the finding and the fix.
- **The orchestrator dispatches; helpers never start other helpers.** One orchestrator per run. Helpers may run in parallel (user, 3 Nov 2026) unless they could conflict over data (writing the same file, sheet range or source rate limit) or one depends on another's result or learnings (e.g. F8-F9 companies, which flow one at a time so each one's learnings reach the next); then one at a time. Parallel helpers do different things: batches of the same step run one after another unless there is a strong reason to run them together. At most 2 helpers at once (user, 4 Nov 2026): an Opus high helper always runs alone; an Opus medium helper may run alongside one Sonnet or Haiku helper only (never two Opus helpers together); scripts and other non-agent tasks don't count. When the user asks for something while that limit is reached (a second helper while an Opus high one runs, or a third), ask the user before starting it. Pause new ones if usage runs low. Default model settings (user, 4 Nov 2026; not absolute): Sonnet low (mechanical work: browser fetches, sheet writes, screens), Opus medium (judgement, reading filings, writing or fixing scripts, debugging, rechecks) and Opus high (only the most complex analysis within a task, saying why); Sonnet medium where a task needs a little more than Sonnet low; Haiku may be tried where almost no thinking is needed (test its accuracy on the task first); avoid Sonnet high (Opus medium does that work more efficiently). After a few runs of a task, suggest a model change to the user when its tokens or time look higher than the work needs. Models and efforts per step: `process/future/README.md` and `process/past/README.md`.
- **Browser fetches** (sources only the browser pane reaches, such as old BSE lists) always go to a helper, never the orchestrator, so the model and effort can be chosen (user, 4 Nov 2026): Sonnet low (Haiku to be tried). The helper only collects what the page shows (links, small tables) into a file with a page script; scripts download and parse the rest. One browser helper at a time (the pane is shared); helpers have the `mcp__Claude_Browser__*` tools.
- **Labels (user, 4 Nov 2026):** every helper, background task and watchdog, and every report about one: `<step> (<batch size or single company symbol>): <standard step name>`, e.g. `P3.24 (25): Business-type tagging`, `P3.36 (OSWALGREEN): Business-type tagging`, `F9.3 (RELIANCE): Deep analysis`; a step that doesn't repeat has no bracket (`P9: Mechanisms`). Every step has its own major number; a repeating step is X.0 in the README tables and its runs are X.1, X.2 … (per-company future steps: the company's position in `company_list.csv`). Rechecks keep R (F4R.n checks F4.n; P10R.n checks P10.n). Numbers and standard names: each workflow README's table.
- Judgement work is rechecked (`process/future/recheck.md`) rather than redone in independent runs. Helpers write bulky data to files and return short summaries. Use Agent-tool helpers, not workflows, unless the user asks.
- Lower a phase's model (also as you learn during runs) only when the lower model can handle it and the higher one had no strong reason, never just to save usage. When strongly confident, make the change and tell the user; when not sure, ask the user first.

## Files and scripts
- **Storage:** budget 20 GB for this project; tell the user when `data/` nears it (~16 GB). Full company downloads (F8) only for companies on `company_list.csv`; earlier phases download only the documents they read. Scratch work stays in the session's scratchpad.
- **Access denied:** if a file operation fails with "access denied" (often the auto permission mode), retry a few times, then tell the user.
- **Scripts:** don't write scripts (or skip a built-in tool) for what the built-in tools can do, unless it saves tokens. Read-only scripts may run without asking; ask before running a script that changes anything outside the project folder (the scratchpad and the project's Google Sheet excepted).
- **Sheet:** final outcomes only; the user reads it only when told all changes are in place. Its layout, colours and which columns each phase writes are in `tools/tools.md` and the phase files.
