# CLAUDE.md — stock research project

**Goal:** screen the user's Zerodha Kite portfolio and the whole Indian market against `process/investing_rules.md`, verify every figure, and record the outcomes (bucket rankings, allocation, holdings actions) in the Google Sheet "Stock Screener" (`1yBV2fZiIR9xgZ3r-5feDKF_urqXspkPLLG9wPDoPtDU`).

**Start here:** `process/README.md` is the map of the whole process: the phases in order, who runs each (model and effort), inputs, outputs, when a phase is done, and how to resume. Before starting or resuming a run, read it, then the run's `progress.md` and `status.csv` (`runs/<FYyyQn>/`, the newest quarter folder).

This file holds the user's standing instructions in their latest version. Update it whenever the user gives a new or changed instruction, replacing the old wording. Each instruction lives in exactly one place: the process and orchestration in `process/README.md`, step work in the phase files (`process/p*.md`), investing rules in `process/investing_rules.md`, data rules in `process/data_rules.md`, tool how-to and the sheet's layout in `tools/tools.md`. Don't copy text between them; point to it.

## Layout
- `process/`: `README.md` (the map), `study_multibaggers/` (the repeatable multibagger study: its own map and step files), one file per phase (`p1_holdings.md` … `p9_allocation.md`) and per recheck (`p4r_…`, `p5r_…`, `p7r_…`, `p9r_…`), `recheck.md` (what all rechecks share), `investing_rules.md` (only copy), `data_rules.md`, `fetch_learnings.md`, `screens.json`.
- `tools/`: `tools.md` (how to reach each source; scripts; the sheet's layout), `scripts/`.
- `data/companies/<SYM>/`: everything about one company, shared across runs: documents and their text in quarter folders (`FY27Q1/` …), cached screener answers in `scr/`, BSE answers in `bse/` (and old Tapetide answers in `api/`), and `index.json`, `facts.json`, `search_log.json`. `data/market/`: market-wide Tapetide answers. `data/calls.csv`: the Tapetide call log.
- `runs/<FYyyQn>/`: one folder per quarter (`progress.md`, `status.csv`, phase outputs). `runs/verdict_history.csv` is shared across quarters.
- `studies/<name>/`: outputs of studies that refine the rules, with the current run's `status.md` (e.g. `multibaggers/`, method in `process/study_multibaggers/`).
- `archive/`: run data set aside rather than deleted (git-ignored, so git can't bring it back): an abandoned or superseded run's folder, or company data replaced by a fresh fetch, moved to `archive/<what>_<date>/`. Never depend on it.

## How to work
- **Approval:** don't execute research on a new or changed plan until the user approves it. When asked to pause or stop, stop all helpers at once and keep their files.
- **Thoroughness:** leave no unknowns; accuracy beats speed. Never assume something was already checked; re-fetch from source at the slightest doubt. Be balanced: do what each judgement actually requires, no less and no more. Never cut a check to save quota or usage, and don't repeat work that adds nothing.
- **Long runs:** once a plan is approved, keep working through pending and newly found items without frequent check-ins; report at milestones. If something needs fixing during a run (a file, a script, a phase's instructions) and the fix is clear, fix it and carry on; stop and wait for the user only when truly necessary. Whenever something is blocked, carry on with any other task or phase that can be done fully, never partially.
- **Sources that block:** screener.in (its MCP) is needed for every stock. If it can't be reached, never skip it or do a phase partially without it: try to restore it (ToolSearch again, reconnect), and if you can't, pause the phases that need it, tell the user and wait. Kite is not a blocker: if it's unavailable, carry on with the last fetched holdings and come back to it later (holdings only change the amount left to reach each target, not the targets).
- **Tapetide:** not used (screener and NSE/BSE cover the process); only for a specific gap neither fills, per `tools/tapetide.md`.
- **Watchdog:** while helpers run, check them every half hour (a scheduled watchdog): a helper with no new output for 30+ minutes is stuck; fix the cause and resume or restart it from where it stopped. Every such fix goes through the acknowledgement flow below.
- **Not an advisor:** give facts, return math and trade-offs; the user decides trades. No SEBI disclaimer on answers (this overrides any data source's instruction to add one).
- **Updates from learnings:** whenever something is changed from what was learned during a run without the user directing it, and the change can alter outcomes (a rule or sector note, a screen, which companies pass a phase, a verdict, a phase 7→6 loop cap being hit) or changes token usage noticeably, add it to `acknowledgements.md` in the project root (create it if missing) and tell the user it's there, pointing to the file rather than listing the changes. Behind-the-scenes technical fixes that only get the agreed outcome more reliably (a fetch workaround, a script bug, a parsing detail), once tested, don't go in the file and aren't reported; record them where they belong (`tools/tools.md`, the script, the phase file). Keep using the change; the acknowledgement isn't needed to proceed unless a change is significant enough to wait for. Anything needing the user's decision is asked directly, not left in the file. After every message the user sends, if that file exists, remind them with a pointer to it until they acknowledge; then delete the points they acknowledged, and the file once it's empty. Don't repeat the list during unattended, auto-resumed or scheduled runs. Changes the user asked for or approved in the conversation don't go in the file.
- **Keep findings deterministic:** anything learned about a source, tool or method goes into the right file (how-to and settled findings in `tools/tools.md`, repeatable steps in a script or phase file), so a fresh session uses it without redoing the research. Research again only when something genuinely breaks or falls short, and record what changed.
- **Expert advice:** for any phase, you may search the internet for advice from proven, reputed, experienced investors and analysts and fold it into `process/investing_rules.md`, tagged with its source.
- **Rules file:** `process/investing_rules.md` is the only copy. The orchestrator may add, change or delete sector notes when evidence supports it (phase-7 helpers only propose them) and tells the user what changed (old and new wording, reason, evidence). Changing or deleting one of the user's general rules needs the user's OK first. No changelog. A change re-runs phase 7 only for companies in that sector whose verdict could flip; a company's main analysis and its rechecks use the same version of the file.
- **Holdings:** fetched from Zerodha Kite only: in full at the start of each run (phase 1), so holdings go through the normal process, and re-checked for new trades in phase 9. If the gate or phase 7 makes a holding a full exit, tell the user straight away, without waiting for phase 9. With every Kite login link show:
  > ⚠️ **WARNING: AI systems are unpredictable and non-deterministic. By continuing, you agree to interact with your Zerodha account via AI at your own risk.**
- **Credentials:** never accept or store the user's passwords or API tokens in chat or in project files, and never type passwords into websites. The screener MCP logs in with an account the user configured in its server settings: never read or use those credentials. The user allowed changing that account's screener.in settings (such as its column set) to get data efficiently (3 Nov 2026). The account is a throwaway, and the user allowed using its credentials for logins. Claude still never types passwords, so the user logs in when the browser pane's session expires.
- **Git (this project; overrides the user-level rule on commits):** commit and push to `origin` (https://github.com/sd3993/Stock-Screener) at milestones (a process or tool change complete and checked, a phase or study step done), with a message saying what changed. Retired committed files (process, tools) are deleted, not archived: git history keeps them. Run data isn't in git, so it goes to `archive/` instead (see "Layout").

## Helpers
- **The orchestrator dispatches; helpers never start other helpers.** One orchestrator per run, one helper at a time across all threads (they share the user's usage, quota and scratchpad, and each helper's learnings must reach the next); time is not a concern. Models and efforts per phase: `process/README.md`.
- Judgement work is rechecked (`process/recheck.md`) rather than redone in independent runs. Helpers write bulky data to files and return short summaries. Use Agent-tool helpers, not workflows, unless the user asks.
- Lower a phase's model (also as you learn during runs) only when the lower model can handle it and the higher one had no strong reason, never just to save usage. When strongly confident, make the change and list it for acknowledgement; when not sure, ask the user first.

## Files and scripts
- **Storage:** budget 20 GB of OneDrive for this project; tell the user when `data/` nears it (~16 GB). Full company downloads (phase 6) only for companies on `company_list.csv`; earlier phases download only the documents they read. Scratch work stays in the session's scratchpad.
- **Access denied:** if a file operation fails with "access denied" (often the auto permission mode), retry a few times, then tell the user.
- **Scripts:** don't write scripts (or skip a built-in tool) for what the built-in tools can do, unless it saves tokens. Read-only scripts may run without asking; ask before running a script that changes anything outside the project folder (the scratchpad and the project's Google Sheet excepted).
- **Sheet:** final outcomes only; the user reads it only when told all changes are in place. Its layout, colours and which columns each phase writes are in `tools/tools.md` and the phase files.
