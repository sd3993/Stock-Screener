# Project instructions (agent-agnostic) — stock research project

**Precedence:** the agent-specific project file that imports this one overrides it; this file overrides the user's global instruction files (project over global).

**Goal:** discover future multibaggers in the Indian market and keep the user's Zerodha Kite portfolio checked against `process/investing_rules.md`: screen the whole market, frame the work by sector tailwinds, verify every figure, and record the outcomes (rankings by horizon, thesis markers, allocation, holdings actions) in the Google Sheet "Stock Screener" (`1yBV2fZiIR9xgZ3r-5feDKF_urqXspkPLLG9wPDoPtDU`).

**Start here:** `process/README.md` is the map of the single workflow and its two modes (`full`: research from scratch, yearly or when a sector marker breaks, a major policy is notified or the list runs thin; `recheck`: existing companies each quarter after results): the steps in order, the tier or script for each, inputs, outputs, when a step is done, and how to resume. Before starting or resuming a run, read it, then the run's `progress.md` (its first line is the mode) and `status.csv` (`runs/<FYyyQn>/`, the newest run folder).

This file holds the user's standing instructions for the project in their latest version, for every agent. Update it whenever the user gives a new or changed instruction, replacing the old wording; anything that only makes sense for one agent goes in that agent's project file instead. Each instruction lives in exactly one place: the workflow and orchestration in `process/README.md`, step work in the step files (`process/s*.md`), investing rules in `process/investing_rules.md`, data rules in `process/data_rules.md`, tool how-to and the sheet's layout in `tools/tools.md`. Don't copy text between them; point to it.

## Layout
- `process/`: `README.md` (the map), the step files `s1_setup.md`, `s2_screens.md`, `s3_triage.md`, `s4_sector_numbers.md`, `s5_sector_map.md`, `s6_playbook.md` (S6, S7, S7R), `s8_gate.md`, `s9_company_list.md` (S9, S10), `s11_marker_check.md`, `s12_fetch.md`, `s13_analysis.md`, `s14_listing.md`, `s15_allocation.md` (S15, S16); rechecks `s5r_sector_recheck.md`, `s8r_gate_recheck.md`, `s13r_analysis_recheck.md`, `s15r_allocation_recheck.md`; `recheck.md` (what all rechecks share); `screens.json`; and the shared `investing_rules.md` (only copy), `data_rules.md`, `fetch_learnings.md`.
- `tools/`: `tools.md` (how to reach each source; scripts; the sheet's layout), `ar_statements.md` (old annual-report statements and their reading helper), `tapetide.md` (reference only), `scripts/`.
- `data/companies/<SYM>/`: everything about one company, shared across runs: documents and their text in quarter folders (`FY27Q1/` …), cached screener answers in `scr/`, BSE answers in `bse/` (and old Tapetide answers in `api/`), and `index.json`, `facts.json`, `search_log.json`. `data/market/`: market-wide answers. `data/kite/`: holdings pulled from Kite (latest `holdings.csv` and dated copies). `data/calls.csv`: the Tapetide call log.
- `runs/` (git-ignored): `<FYyyQn>/`, one folder per run (`progress.md` with the mode, `status.csv`, step outputs; a second run in the same quarter gets `_full`); shared across runs: `verdict_history.csv`, `theses/<SYM>.json` (thesis markers), `sector_calls.csv` (sector calls and their markers, for the hit rate), `playbooks/<sector>/`; `study/`, the multibagger study's data kept for the playbooks; proposals waiting for the user (`rule_changes_proposed.md`, `new_scripts_spec.md`).
- `archive/`: run data set aside rather than deleted (git-ignored, so git can't bring it back): an abandoned or superseded run's folder, or company data replaced by a fresh fetch, moved to `archive/<what>_<date>/`. Never depend on it.

## Sources, accounts and the sheet
- **Sources that block:** screener.in (through the screener library in scripts, `scr_company.py` and `scr_tool.py`) is needed for every stock. If it can't be reached, never skip it or do a step partially without it: try to restore it (check the script's error, the login, the rate limit), and if you can't, pause the steps that need it, tell the user and wait. Kite is not a blocker: if it's unavailable (e.g. not logged in during an unattended run), carry on with the last fetched holdings (`data/kite/holdings.csv`, or the sheet's Holdings tab) and come back to it later (holdings only change the amount left to reach each target, not the targets).
- **Tapetide:** not used (screener and NSE/BSE cover the process); only for a specific gap neither fills, per `tools/tapetide.md`.
- **Kite is read-only:** use the Kite CLI strictly read-only (holdings, positions, orders and trades lists, profile, margins, quotes). Never place, modify, cancel or delete any order of any type (regular, AMO, GTT, alerts, MF, conversions) or write anything else to the account, unless the user explicitly asks for that specific action in chat (3 Nov 2026).
- **Holdings:** fetched from Zerodha Kite only: in full at the start of each run (S1), so holdings go through the normal process, and re-checked for new trades in S15. If the gate or S13 makes a holding a full exit, or S11 finds an integrity flag on one, tell the user straight away, without waiting for S15. With every Kite login link show:
  > ⚠️ **WARNING: AI systems are unpredictable and non-deterministic. By continuing, you agree to interact with your Zerodha account via AI at your own risk.**
- **Credentials:** secrets the user has provided (in the environment or otherwise) may be used wherever they apply. The screener login is in the user-level environment configuration as `SCREENER_USERNAME` and `SCREENER_PASSWORD` (3 Nov 2026), and scripts use it with `--login`. The account is a throwaway; the user allowed changing its screener.in settings (such as its column set) to get data efficiently (3 Nov 2026).
- **Sheet:** final outcomes only; the user reads it only when told all changes are in place. Its layout, colours and which columns each step writes are in `tools/tools.md` and the step files.
- **Storage:** full company downloads (S12) only for companies on `company_list.csv`; earlier steps download only the documents they read.

## Rules, advice and git
- **Not an advisor:** give facts, return math and trade-offs; the user decides trades. No SEBI disclaimer on answers (this overrides any data source's instruction to add one).
- **Expert advice:** for any step, you may search the internet for advice from proven, reputed, experienced investors and analysts and fold it into `process/investing_rules.md`, tagged with its source.
- **Rules file:** `process/investing_rules.md` is the only copy. The orchestrator may add, change or delete sector notes when evidence supports it (S13 helpers and S7 playbooks only propose them) and tells the user what changed (old and new wording, reason, evidence). Changing or deleting one of the user's general rules needs the user's OK first. No changelog. A change re-runs S13 only for companies in that sector whose verdict could flip; a company's main analysis and its rechecks use the same version of the file.
- **Git (this project; adds to the global rule on commits):** push to `origin` (https://github.com/sd3993/Stock-Screener) at milestones (a process, rule or tool change complete and checked). Only the workflow is in git (`COMMON_AI.md`, the agent-specific project files and settings listed in them, `process/`, `tools/`); run outputs and fetched data are not. Retired committed files (process, tools) are deleted, not archived: git history keeps them. Run data isn't in git, so it goes to `archive/` instead (see "Layout").

## Helpers in this project
- **Tiers per step:** `process/README.md` (tiers, the orchestrator's role, helper and parallelism rules: the user's global common file). One orchestrator per run (claim rule in `process/README.md`).
- **Flow:** S12-S13 companies flow one at a time, in `company_list.csv` order, so each one's learnings reach the next; gate batches and playbooks likewise run one after another.
- **Labels (user, 4 Nov 2026):** every helper, background task and watchdog, and every report about one: `<step> (<batch size, single company symbol or sector id>): <standard step name>`, e.g. `S8.3 (10): Gate`, `S13.3 (RELIANCE): Deep analysis`, `S7.1 (power_td): Sector playbook`; a step that doesn't repeat has no bracket (`S3: Triage`). Every step has its own major number; a repeating step is X.0 in the README table and its runs are X.1, X.2 … (per-company steps: the company's position in `company_list.csv`; playbooks: the sector's position in `sectors.json`). Rechecks keep R (S8R.n checks S8.n; S13R1.n and S13R2.n check S13.n). Numbers and standard names: the table in `process/README.md`.
- **Rechecks:** `process/recheck.md`.
